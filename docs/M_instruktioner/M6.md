Spår 1 · Inloggningen (1–2 pers)

Målet: en kund loggar in med e-post och lösenord, och den fejkade localStorage.kraftly_logged_in är borta ur hela koden.

    Token i minnet. Skapa src/services/token.js som håller access token i en variabel (inte i localStorage):

    import { ref } from 'vue'
    const accessToken = ref(null)
    export const getAccessToken = () => accessToken.value
    export const setAccessToken = (t) => { accessToken.value = t || null }

    LoginView anropar /api/v2/auth/login med e-post och lösenord, sparar token med setAccessToken, och visar ett felmeddelande med role="alert" vid fel uppgifter. Ingen localStorage.setItem någonstans.
    Refresh. I API-klienten: vid 401, gör ett POST /api/v2/auth/refresh (refresh-cookien följer med automatiskt, den är satt av API:t), spara den nya token, och gör om anropet en gång. Vid omladdning: be om en ny token vid appstart (så att man inte loggas ut av en F5).
    Sök igenom repot efter kraftly_logged_in och localStorage – allt som hörde till fejk-loginen ska bort, även i gamla tester och guards.

Klart när: man loggar in med rätt uppgifter, får fel med fel uppgifter, localStorage är tomt efter inloggning (kolla i DevTools), och en omladdning behåller inloggningen.
Spår 2 · Anropen och skyddet (1–2 pers)

Målet: appen pratar med v2, och API:t släpper inte fram data utan token.

    api.js mot /api/v2, med Authorization: Bearer <token> från token.js. Ta bort credentials: 'include' om det finns – dataanrop ska bäras av token, inte av en cookie.
    Route guard som skickar utloggade till /login. Skriv en kommentar om att guarden är UX – skyddet sitter i API:t.
    Bevisa skyddet: curl -s -o /dev/null -w "%{http_code}" https://<staging>/api/v2/invoices ska ge 401 (utan token). Klistra beviset i docs/security.md. Skriv gärna ett test som anropar en skyddad endpoint utan token och kräver 401.
    Data ur token, inte ur anropet. Om fakturasidan (eller någon annan) skickar med ett id eller customerNo: ta bort det. API v2 väljer datan ur token; visa (curl eller test) att en tillagd querystring ignoreras.

Klart när: appen fungerar mot v2, curl utan token ger 401, och ingen endpoint väljer data utifrån något klienten skickar.
Spår 3 · Headers och CSP (1 pers)

Målet: en Content Security Policy och säkerhetsheaders på varje svar, och CORS som inte är vidöppen.

    docker/security-headers.conf med CSP (default-src 'self'; script-src 'self'; …; frame-ancestors 'none'), X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy, och HSTS.
    Inkludera den i VARJE location i nginx.conf.template som har egna add_header – nginx ärver inte add_header från server-blocket så fort en location har en egen. (Det var fällan i cache-blocken från vecka 6.)
    CORS: går alla API-anrop genom er egen proxy (samma origin)? Då behövs ingen CORS – bäst. Om något behöver riktig CORS: en uttrycklig lista över origins, aldrig * med cookies.
    Bevis: curl -I https://<staging>/ | grep -i -E 'content-security|x-frame|x-content' – klistra utdraget i docs/security.md.

Klart när: curl -I på staging visar CSP och de andra headrarna, även på /assets/ och /index.html.

M6 – Säkrad

    Inlämningsdatum 6 Okt av 23.59 Poäng 0 Lämnar in en textimatningsruta

Sjätte milstolpen i Kraftly-projektet. Målet: portalens fejkade inloggning är borta. En kund loggar in med riktiga uppgifter, och API:t släpper inte fram några data utan ett giltigt bevis på vem kunden är. Ni har gått igenom OWASP Top 10 mot er egen portal, lagat det ni hittade, och skrivit ner det i docs/security.md. CORS är låst till era egna adresser och en Content Security Policy ligger på.

    Den fejkade inloggningen (localStorage.kraftly_logged_in) och de öppna endpointsen var skuld nummer 6 i docs/debt.md. Det är den ni betalar av nu.

Vad som är nytt i mock-API:t

Kraftlys test-API har fått en v2 med riktig autentisering (samma för alla team). Den gamla /api/… (v1) finns kvar men är märkt Deprecation/Sunset och avvecklas 13/10 – bygg mot v2.

    POST /api/v2/auth/login → access token (JWT, 10 min) i svaret + refresh token i en httpOnly-cookie
    POST /api/v2/auth/refresh → ny access token (mot cookien), POST /api/v2/auth/logout
    GET /api/v2/user, /invoices, /consumption, POST /api/v2/move – kräver Authorization: Bearer <token>, och väljer data ur token, aldrig ur ett id i anropet

Testkonton står på Canvas-sidan Testkonton v.7.
Definition of Done

Bocka av i docs/milestones.md under rubriken M6. Alla punkter ska vara uppfyllda på main när taggen sätts.

    Riktig inloggning: LoginView loggar in mot /api/v2/auth/login med e-post och lösenord, visar ett felmeddelande vid fel uppgifter (role="alert"), och den fejkade localStorage-flaggan är borttagen ur hela koden
    Access token i minnet, inte i localStorage: ett test eller en kort motivering i docs/security.md som visar att token inte hamnar i webblagring. Refresh sköts mot cookien; en omladdning loggar inte ut
    Skyddade routes + skyddat API: en route guard skickar utloggade till /login, och ni har visat (curl eller ett test) att /api/v2/invoices svarar 401 utan token – guarden är UX, API:t är skyddet
    Ingen kund ser en annans data: fakturor/förbrukning väljs ur token. Om ni bygger en variant med ?customerNo= eller liknande: visa att den ignoreras (A01/IDOR)
    OWASP-genomgång i docs/security.md: en rad per relevant kategori (minst A01, A02, A05, A07) med vad ni hittade och vad ni gjorde. Använd mallen (Canvas-sidan OWASP-checklista)
    CORS låst: API-anropen går genom er egen proxy (samma origin). Om något behöver riktig CORS: en uttrycklig lista över origins, aldrig * med cookies. Skriv motiveringen i docs/security.md
    Content Security Policy + säkerhetsheaders: CSP (minst default-src 'self'; script-src 'self') plus X-Content-Type-Options, X-Frame-Options/frame-ancestors satt i nginx. curl -I på er staging som visar dem, klistrat i docs/security.md
    Ett beslutsdokument docs/decisions/tokenlagring.md: var access token lagras, alternativen (localStorage / cookie / minne), och varför ni valde som ni valde
    Testerna gröna (inklusive minst ett nytt test på auth-flödet eller att ett skyddat anrop kräver token) · logg i docs/log.md

Valfritt (räknas inte i DoD): byt hela egen-inloggningen mot ett OIDC-login mot en leverantör (Auth0/Entra/Keycloak) och beskriv flödet i docs/security.md – ett starkt VG-samtal · en Sunset-hantering i klienten som varnar när v1 används · rate limiting-test mot login.

Vanliga missar – kolla innan ni taggar

    Token i localStorage "för att det var enklast" → hela poängen med veckan borta. I minnet, med refresh mot cookien

    CSP är satt i server-blocket men försvinner i location-blocken med egna add_header → nginx ärver inte add_header. Inkludera säkerhetsheadrarna i varje location (se övning 2)
    Access-Control-Allow-Origin: * kvar från förra byrån, särskilt med cookies → lista era origins, eller kör allt genom proxyn så behövs ingen CORS
    Den fejkade localStorage.kraftly_logged_in ligger kvar någonstans (t.ex. i en gammal guard eller ett test) → sök igenom repot, den ska vara helt borta
