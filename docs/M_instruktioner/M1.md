Syfte

M1 kräver "teststrategi dokumenterad i docs/testing.md". Det är inte ett formkrav – det är beslutet om vad ni testar var, och varför, så att nästa vecka (CI) och veckorna efter (auth, prestanda, komponentbibliotek) har en regel att luta sig mot. Ett dokument på en sida räcker. Ett dokument som ingen i teamet kan försvara muntligt räcker inte – det är precis vad som frågas på avstämningar och VG-pass.

Tumregler att bryta mot medvetet: ren logik → enhet. Något med markup och interaktion → komponent. Ett flöde över flera sidor eller mot riktigt API → E2E (Cypress – ni kan det från kurs 2). Om ni vill testa något på två nivåer: motivera det.
Del 2 · Fem beslut (20 min)

Skriv ned teamets svar. Kort. Varje beslut ska gå att läsa upp på 20 sekunder.

    Vad testar vi inte, och varför? (Chart.js? CSS? Routerns interna beteende?)
    Hur mockar vi API:et? Modulmock (vi.mock) i komponenttester, riktigt mock-API i E2E, eller något annat? En regel, inte per test.
    Vad krävs för att en PR ska få mergas när det gäller test? Alla gröna är självklart. Måste ny logik ha nytt test? Måste en buggfix ha ett regressionstest? (Facits svar: ja på det senare – och det är en bra regel.)
    Täckningskrav – ja eller nej? Ett vanligt reflexval är "80 % coverage". Vad garanterar det faktiskt? Vad garanterar det inte? Bestäm er, och skriv varför.
    Namngivning & placering. *.test.js bredvid koden eller i tests/? Testnamn på svenska eller engelska? (Koden är på engelska. Testnamn läses av människor – bestäm.)

M1 – Kvalitetsgrund

    Inlämningsdatum 1 Sep av 23.59 Poäng 0 Lämnar in en textimatningsruta

Andra milstolpen i Kraftly-projektet. Målet: portalen har ett skyddsnät. Varje ändring möts från och med nu av tester och en kvalitetsgrind innan den ens blir en commit – och teamet har bestämt, skriftligt, vad som testas var och varför. Det här är grunden som nästa veckas CI-pipeline bygger på: utan tester är pipelinen en tom grind.
Definition of Done

Bocka av i docs/milestones.md under rubriken M1. Alla punkter ska vara uppfyllda på main när taggen sätts:

    Testsvit med minst 10 meningsfulla test – både logik (enhet) och komponent, körbara med npm run test:run, alla gröna
    Minst 5 av testerna är på kod som inte var med i torsdagens övningar (stores, api.js, LoginView, ProfileView, spinnern, det svalda felet …)
    Minst ett regressionstest på en bugg ur er docs/debt.md – ett test som hade fångat buggen om den funnits kvar. Skriv i testnamnet eller en kommentar vilken skuld det gäller
    ESLint + Prettier körs i pre-commit via husky + lint-staged. npm run lint och npm run format:check går igenom på main utan errors
    Teststrategi i docs/testing.md enligt strukturen från workshopen: nivåer, karta över vad som testas var, era fem beslut (inkl. täckningskrav ja/nej och varför), vad ni medvetet inte testar
    E2E-beslutet dokumenterat i docs/decisions/e2e-verktyg.md (se nedan), och det valda verktygets smoke-test mergat till main (körbart med npm run e2e:pw eller npm run e2e:cy)
    Logg i docs/log.md: en post per arbetsdag – vad ni gjorde, vad som var svårt, vem som gjorde vad

Meningsfulla betyder: varje test skulle fånga en riktig bugg om den återkom. Tio bra test slår trettio tomma. Tester som testar Vue, Chart.js eller ett klassnamn räknas inte.
Om beslutsdokumentet

Ett beslutsdokument är en halv sida som fångar ett tekniskt beslut: vad ni valde, varför, vad ni valde bort och vad det kostar er. Poängen är att den som läser koden om tre veckor – ni själva, eller nästa tech lead – slipper undra "varför gjorde vi så här?". Ni kommer skriva flera under kursen, en fil per beslut i docs/decisions/. Det här är det första och gäller Boiler Room-fredagens val av E2E-verktyg. Mall:

# Beslut: verktyg för E2E-tester

**Datum:** 2026-08-28
**Beslut:** Vi använder ___ för end-to-end-tester.

## Bakgrund

Vad behövde vi lösa?

## Alternativ vi jämförde

Cypress och Playwright – era egna observationer från workshopen:
tid till första gröna test · hur man hittar element · mockning · väntan/flakiness · headless i CI · felmeddelanden

## Motivering

Varför det här, med era ord. Två–fyra meningar.

## Konsekvenser

Vad vi ger upp. Vad som krävs för att byta senare.

Kravet är inte längd – det är att alla i teamet kan läsa upp beslutet och motiveringen på 30 sekunder på onsdagens avstämning.
Så taggar ni M1

Taggen sätts av tech lead, på main, efter att sista PR:en mergats:

git switch main
git pull
npm run test:run && npm run lint # båda gröna? annars är ni inte klara
git tag -a M1 -m "M1 Kvalitetsgrund"
git push origin M1

Kontrollera under Tags på GitHub att M1 finns och pekar på rätt commit. Taggen flyttas inte. Kommer ni på något efteråt gör ni det i en ny PR och skriver i loggen vad som kom efter.
Inlämning – enskilt, precis som M0

Var och en i teamet lämnar in som text:

    Länk till teamets repo på GitHub
    Länk till taggen (https://github.com/<org>/<repo>/releases/tag/M1)
    Ditt bidrag: länk till en PR eller ett test som du skrivit i M1, plus en mening om vad det gör

Taggen är gemensam, men inlämningen är din. Punkt 3 är samma fråga som självskattningsmatrisen ställer i slutet av kursen – var i underlaget syns ditt arbete – så vänj dig vid den nu. Ingen rapport, inga skärmdumpar; allt annat finns i repot. Teamets reflektion (mest/minst nöjda med, vilket test ni skulle visa upp) skriver ni i docs/log.md.
Vad som händer på onsdag 2/9

Teamrunda ~5 min per team. Jag ber er om tre saker: läsa upp E2E-beslutet på 30 sekunder, peka på ett test och förklara vilken rad i docs/testing.md som motiverar att det ligger på den nivån, och visa att hooken stoppar en fulcommit live. Alla i teamet ska kunna svara – inte bara den som skrev koden.
Vanliga missar – kolla innan ni taggar

    npm test startar watch-läget och blir aldrig klart – det är därför test:run ska finnas
    Hooken vägrar testfilerna med 'it' is not defined → importera från vitest eller lägg till Vitest-globalerna i eslint.config.mjs (demo-guiden)
    Tester som failar bara ibland → något använder new Date() eller riktigt nätverk. Skicka in tiden, mocka anropet
    docs/testing.md som beskriver testpyramiden i allmänhet istället för er kodbas – det är kartan och besluten som räknas
    Taggen satt på en feature-branch istället för main
